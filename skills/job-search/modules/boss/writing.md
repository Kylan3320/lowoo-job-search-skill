# BOSS 直聘招呼语

以候选人口吻代拟第一条消息，让招聘方一眼看到相关经历。这里的写法帮助选经历和措辞，交稿直接给招呼语。语气和节奏优先参考本次用户给出的改稿，或安装目录中已有的 `profile/招呼语正反例.md`。缺少个人改稿时，参考[表达正反例](examples.md)的取材、顺序和语气。

## 开头先亮出岗位最看重的优势

从 JD 的核心职责和筛选条件出发，对照候选人已经证实的经历，选出最能让 HR 愿意继续读的优势。把它放在开头第一个短语里，让人只看到前几个字也能认出匹配点。使用当前求职者自己的简历、画像和亲改稿判断。例如，对口实习次数、覆盖的业务端、独立做成的产品或有依据的业务成果，都可能成为第一眼最有价值的信息。若一项专项成果更能证明胜任，就让它先出现。

首句保留有区分度的限定，例如业务端、独立承担的范围或直接对口的实习经历。下一句顺着首句里最贴 JD 的那一点，直接讲候选人在什么项目里做了什么决定，或交付了什么。首句已经把产品和交付讲清时，可直接补结果。两句连读应当能回答同一个招聘问题。JD 的出勤硬条件接在这项证据之后，放在首段末。

## 正文选什么证据

先确定 JD 中最需要证明的能力，再从同一项目的正式材料里选择最有区分度的事实。比较能说明成果、验证规模、产品取舍或交付边界的材料，再决定哪项值得写。若某句换成别的候选人也说得通，回到具体决定、验证或结果。请求附作品只改变文末入口；有链接本身不能顶替正文里的证明。

压缩时先保住这项证据及必要条件，再删泛泛自评、功能清单、过程数量和重复履历。JD 另有重要职责且现有证据尚未覆盖时，才补一段。两段之间各自说清项目和个人贡献。岗位关心执行链路就讲任务边界或数据流转，关心验收就讲如何验证及其依据。交付了原型但没有成效数据时，可以写清要解决的问题、做出的具体设计和实际交付到哪一步。

## 事实与措辞

用用户本轮明确确认的事实和指定简历选取证据。已有 `profile/求职画像.md` 时，用其中的资料入口和已确认的项目事实补充本次材料。正反例只用于学表达；遇到有时间性的数字，沿用本轮指定版本，无法确认时可省掉数字。能用现有证据写出可信正文时直接交稿，略去未确认的数字或出勤承诺。只有关键事实缺失、现有材料无法解决且答案会实质改变稿子时，才在出稿前问一个具体问题，例如「这次推广中，你负责用户触达、引导还是复盘？」多份 JD 共用的缺口只问一次，其余能完成的岗位照常交付。

用候选人会发给招聘方的正式聊天语言。介绍产品时直接说谁可以用它做什么。岗位看重某项产品判断或操作设计时，才展开那个细节。按问题组织句子，避免模拟用户台词、连续追问或逐步报操作过程。

有数据时，选能改变招聘判断的数字。成果用已核实的改善，评测规模用真实用例量，持续迭代可用对应时期的发布记录。范围和测试条件会改变数字的含义时一并保留。有多组数据时，优先留下最能证明岗位核心能力的一组；样本量、版本数或测试耗时各自只证明对应事实。没有量化结果就用可核验的决定与交付，不推算收益。

交稿前单读首句的第一个短语，再和下一句一起读：前者要亮出优势，后者要证明它。回看删减后的证据是否还足以支持首句，对照来源核对贡献、数字与适用条件。

## 收尾与交稿

最后一项相关证据写完就接用户惯用的结束语。末段从已有证据转去罗列工具、作品站、另一段履历或笼统兴趣时，删去这段追加内容。亲改稿里出现过的作品邀请只适用于当时的投递要求。

用户或招聘方明确要求看作品时，从已介绍的项目中选一个最贴岗且可分享的作品，正文直接给出资料中已确认的链接。JD 仅说有项目经验或 Demo 可加分时，可用项目经历满足该项。无需主动提出再发材料。没有已核实的入口时，在稿外说明缺少什么。

出勤放在首段证据之后，身份与承诺连写。定稿后将含届别和出勤的**实际拟发正文**以 UTF‑8 输入 [出勤标点检查](../../scripts/availability.py)（用 Python 运行，标准输入读全文，标准输出给最终正文）。交付或写入文件时使用其输出；此后若再改稿，重新检查。检查只移除身份和承诺之间的逗号，其他标点与已确认的天数、时长原样保留。

只要开头或局部改稿时给相应片段；完整稿按[逐岗交付](delivery.md)返回。
